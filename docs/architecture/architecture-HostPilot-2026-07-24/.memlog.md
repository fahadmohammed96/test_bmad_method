- 2026-07-24 [decision] Paradigma: monolite modulare a strati con eventi di dominio via transactional outbox. Alternative valutate: microservizi (scartati: team piccolo/agenti, scala pilota, costi operativi), serverless (scartato: job schedulati durevoli e worker long-running centrali al prodotto), monolite non modulare (scartato: 6 domini distinti costruiti da story indipendenti divergono senza confini espliciti). Binds: tutto. Prevents: accoppiamento incrociato tra domini e integrazioni sincrone fragili tra moduli.
- 2026-07-24 [decision] Stack: backend Python 3.13 + FastAPI + SQLAlchemy 2 + Alembic + Pydantic v2; DB PostgreSQL 18; frontend Next.js 16 (App Router, TypeScript). Motivazione: template di squadra candidati (frontend-next, backend-fastapi in test-multica) = boring technology per il team; FastAPI dà OpenAPI nativo per il client tipizzato; Postgres copre dati, coda job e audit senza infrastruttura aggiuntiva. Alternative: Django (+admin gratis per config normativa, ma template di squadra assenti e meno adatto ad API tipizzate); Node full-stack Next.js (un solo linguaggio, ma worker durevoli e SOAP meglio serviti da Python). Python 3.13 (non 3.14) per maturità dell'ecosistema librerie.
- 2026-07-24 [decision] Multi-tenancy: DB singolo condiviso, host_id su ogni riga tenant, scoping obbligatorio nel layer repository. Alternative: schema-per-tenant (scartato: overhead migrazioni per decine di host), RLS Postgres (rinviato: complementare, attivabile in seguito senza cambiare il modello).
- 2026-07-24 [decision] Semantica temporale unica: notti come intervalli semiaperti [check_in, check_out) su date locali Europe/Rome; sovrapposizione = intersezione non vuota; timestamp persistiti in UTC; scadenze normative calcolate in Europe/Rome. Prevents: due moduli che calcolano overlap o scadenze in modo diverso (il bug più costoso possibile per SM-1/SM-2).
- 2026-07-24 [decision] Sync iCal: poller pull per Feed con intervallo configurabile; pipeline fetch→parse→normalizza→upsert idempotente con chiave (feed_id, ical_uid); ogni run registrato (SyncRun con esito e timestamp per NFR-2); l'import non cancella mai Prenotazioni — la scomparsa dal feed marca stato `rimossa_dal_feed`; rilevazione Conflitti = funzione pura ricalcolata dopo ogni import; Conflitto con identità stabile (struttura + coppia prenotazioni), stati `rilevato`→`gestito`, riapertura se la sovrapposizione persiste nei sync successivi oltre finestra configurabile (raccomandazione UX UJ-2 accolta).
- 2026-07-24 [decision] Il sistema non scrive mai verso le OTA e non modifica/cancella mai Prenotazioni autonomamente; la risoluzione dei Conflitti è sempre un'azione esplicita dell'Host con istruzioni guidate (FR-6).
- 2026-07-24 [decision] Motore prezzi: valutazione pura e deterministica on-demand (nessun prezzo materializzato come fonte di verità); ogni prezzo calcolato porta la catena di Regole applicate (spiegabilità richiesta dalla UX UJ-5); precedenza fissa proposta: last-minute > weekend > stagione > prezzo base, soggiorno minimo come vincolo ortogonale (da ratificare al G3, PRD §13.1); export CSV.
- 2026-07-24 [decision] Adempimenti: macchina a stati unica (da_fare/in_sospeso/completato/non_applicabile) per tutti e 4 i tipi + contratto plugin per tipo (trigger, calcolo scadenza, preparazione payload, submit opzionale, evidenza). Livello di automazione per tipo = configurazione (G2-A). Transizione a `completato` SOLO per conferma esplicita dell'Host o esito di trasmissione registrato — mai automatica (SM-C2 = 0).
- 2026-07-24 [decision] Alloggiati Web: MVP = compilazione assistita (generazione tracciato ministeriale txt + upload guidato sul portale); invio automatico = adapter SOAP WS_ALLOGGIATI (WSKEY) come fast-follow dietro lo stesso contratto plugin, attivabile per configurazione senza ridisegno. Coerente con la raccomandazione G2-A Opz.2.
- 2026-07-24 [decision] Scheduling durevole: ogni scadenza, promemoria, messaggio automatico e tick di sync è una riga `job` in Postgres (due_at, tipo, payload, stato, tentativi); worker dedicato con claim SELECT…FOR UPDATE SKIP LOCKED; at-least-once + handler idempotenti; vietato ogni timer solo in-memory (NFR-3: le scadenze sono la funzione di fiducia). Alternative: Celery+Redis (scartato per l'MVP: un'infrastruttura in più senza necessità alla scala pilota; migrabile dietro la stessa interfaccia).
- 2026-07-24 [decision] Dati identità Ospiti: tabella segregata `ospite_documento` con soli campi richiesti dal tracciato Alloggiati; cifratura applicativa a campo AES-256-GCM con envelope encryption (DEK per record, KEK in secret manager); retention automatica via job (N giorni dopo `completato`, N configurabile — G2-D); l'evidenza/audit conserva solo prova non sensibile (timestamp, esito, hash ricevuta); UI non ri-espone i dati per default (UX §5.2).
- 2026-07-24 [decision] Regime fiscale: valore derivato (count Strutture attive), mai persistito come stato autonomo; evento di transizione 2→3 e 3→2 genera/ritira il pannello informativo (FR-17, UX UJ-4). Contenuto sempre informativo con disclaimer.
- 2026-07-24 [decision] Messaggi automatici: event-driven dal ciclo di vita Prenotazione via job durevoli; canale MVP = email; contatto Ospite assente dal Feed → task "da inviare manualmente" per l'Host, mai drop silenzioso (risponde alla domanda aperta PRD §13.2).
- 2026-07-24 [decision] API: REST JSON sotto /api/v1, errori RFC 9457 (problem+json), OpenAPI generato da FastAPI, client TypeScript generato per il frontend. AuthN: email+password con hash argon2id, sessione server-side con cookie HttpOnly SameSite=Lax; MFA rinviata.

Prevents: deriva di traduzione (property/unit/listing per la stessa entità) tra story indipendenti.
- 2026-07-24 [decision] Deployment: 3 container (frontend, api, worker) + Postgres gestito; regione UE esclusiva (residenza dati GDPR); ambienti dev/staging/prod; migrazioni Alembic forward-only; backup giornalieri con test di restore.
